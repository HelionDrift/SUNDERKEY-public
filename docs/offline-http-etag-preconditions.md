# Supplied HTTP ETag precondition arithmetic

This R0 component compares caller-supplied selected-representation facts and structured entity-tag preconditions. It does not send a request, observe an origin, choose a representation, authorize a method, or issue an HTTP response. Its conditional status labels are arithmetic observations under the supplied premises. All effects are `none`; positive-use and qualification flags remain false.

The exact registered ownership is profile `AOE-GB-D05-S01`, capability `army.gb.d05.s01`, vector `AV-GB-D05-S01-01`, work package `IWP2-AOE-GB-D05-S01`, wave `IW2-001`, commander `AOE-GB-D05-CMD`, group `AOE-HQ-04`, independent validator `AOE-HQ-34`, and blueprint `sha256:fa6415a05aa9b97e2ca9fa46194d2adc43bb4aabd2a4cfe3b171215d52b18532`. It is partial A7.4 evidence only.

## Closed model and public API

The ten exact source fields are `schema_version: 1`, bounded `source_id`, `recipient_role: "origin"`, `baseline_preconditions_eligible: bool`, `method: "GET" | "HEAD" | "PUT"`, `target_has_current_representation: bool`, `selected_representation_exists: bool`, `selected_entity_tag`, `if_match`, and `if_none_match`. The selected tag is null or `{ "weak": bool, "opaque_tag_base64": canonical_base64 }`. A false selected-existence declaration requires a null selected tag. Selected existence implies that the target has some current representation, but the target may have another current representation when the selected one does not exist. Each condition is null, `{ "mode": "any", "tags": [] }`, or `{ "mode": "tags", "tags": [entity_tag, ...] }`. This is structured input, not a raw HTTP field parser. The opaque tag bytes are exact RFC 9110 entity-tag octets, including empty and high-bit opaque bytes. No Unicode normalization or textual tag decoding occurs.

`analyze_supplied_http_etag_preconditions(model)` accepts an exact native model. `analyze_supplied_http_etag_preconditions_bytes(*, model_bytes)` accepts bounded ASCII JSON bytes. `HttpEtagPreconditionsAnalysis` supports direct construction from retained canonical JSON, `from_dict`, `from_json`, `to_dict`, and `to_json`. `verify_supplied_http_etag_preconditions_analysis(report, *, model)` rederives the embedded original and the separately supplied original within one operation budget, and requires the entire report and address to agree. `component_fixture()` returns a fresh synthetic, nonoperational example. The report retains the complete original model and labels a separate source-model digest and report digest; it is not sanitized for publication.

## Selected arithmetic

Per [RFC 9110, Section 8.8.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.3.2), strong entity-tag comparison requires both tags to be nonweak and their opaque bytes to match. Weak comparison requires matching opaque bytes regardless of weakness. The `*` form of either supplied condition compares the distinct declaration that the target resource has any current representation, even if the selected representation does not exist. A tag list compares candidates only with the selected entity tag.

The caller's `baseline_preconditions_eligible` is a declaration that the ordinary precondition-evaluation gate has been met, not an independently checked status or resource state. If it is false, neither condition is evaluated. Otherwise [RFC 9110, Sections 13.1 and 13.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2.2) order If-Match before If-None-Match. A failed If-Match stops evaluation of If-None-Match. A failed If-None-Match is labeled as a conditional 304 predicate for GET or HEAD and a conditional 412 predicate for PUT. A failed If-Match for GET or HEAD is labeled as a conditional 412 predicate. For PUT, its label explicitly leaves the actual response status unassessed because RFC 9110 permits a 2xx response when the requested unsafe change is already reflected in the current state. No label means a response was sent or a mutation happened.

Other conditional fields, Date validators, If-Range, extension methods, caches, Range, raw header folding, and response construction are outside this component. The model asserts origin-role context only; it does not verify server ownership, currentness, representation selection, normal-response eligibility, or the already-applied exception. This component cannot transfer authority from an input or report.

## Refusal and bounded replay

Exact native scalar families are checked before capture and addressing: bool is not int, float is not int, subclasses and unexpected fields are refused. The byte entry scans raw JSON depth, nodes, strings and signed64 integer grammar before its JSON decoder. Duplicate object members, cycles, noncanonical base64, invalid tag octets and malformed condition forms are refused. A cohashed altered outcome, observation, scope, effect or source is not accepted as a replay of the supplied source.

Model and report ceilings are 64 KiB and 256 KiB canonical ASCII respectively, with 4,096 and 16,384 nodes, depth 12, 512 opaque tag bytes and 16 candidates per field. Each public operation has a 16 MiB cumulative local software-work budget. Its complete planned source/report retention, encoding, equality and address work is reserved before that operation's first SHA-256. Separate-original verification funds both source plans within the same budget. These are software resource ceilings, not estimates of a server's work. A report may be well-formed but refused under a smaller configured local budget.

The source model is embedded for historical arithmetic replay. Such replay is not evidence that the declared resource facts were ever true, remain current, or constitute an authorization or qualification.
