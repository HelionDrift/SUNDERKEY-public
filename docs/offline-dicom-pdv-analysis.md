# Supplied DICOM P-DATA-TF PDV structure

This R0 component inspects one complete, caller-supplied DICOM P-DATA-TF PDU as inert bytes. It does not open a network connection, observe an association, interpret a DICOM message, process patient content, act clinically, or authorize use. All effects are `none`, and authority, positive-use and qualification flags remain false. Use synthetic fragments only: the report embeds the complete supplied PDU bytes as base64 and is not a de-identification or publication tool.

The exact existing registry ownership is profile `AOE-GD-D25-S12`, capability `army.gd.d25.s12`, vector `AV-GD-D25-S12-01`, package `IWP2-AOE-GD-D25-S12`, wave `IW2-012`, commander `AOE-GD-D25-CMD`, group `AOE-HQ-06`, independent validator `AOE-HQ-33`, and blueprint `sha256:8e9af3b53e84ef732bd0cfff19b58d3f0734288d78e757533adaded191735754`. ## Closed source and public API

The source model has exactly three fields: `schema_version: 1`, bounded printable `source_id`, and canonical `pdu_base64`. It represents one complete PDU, not a byte stream of several PDUs. `analyze_supplied_dicom_pdv(model)` accepts exact native JSON families. `analyze_supplied_dicom_pdv_bytes(*, model_bytes)` accepts bounded ASCII JSON bytes. `DicomPdvAnalysis` supports direct construction from retained canonical JSON, `from_dict`, `from_json`, `to_dict`, and `to_json`. `verify_supplied_dicom_pdv_analysis(report, *, model)` compares the full embedded source derivation with a separately supplied original within one software-work budget. `component_fixture()` returns a fresh wholly synthetic two-PDV example. The report retains both the source model and exact PDU byte digest. The source and report have different hash domains.

## Finite structural observations

[PS3.8 Section 9.3](https://dicom.nema.org/medical/dicom/current/output/chtml/part08/sect_9.3.html) specifies big-endian byte ordering for upper-layer PDU headers, not for the unexamined DICOM message fragments. [Section 9.3.5](https://dicom.nema.org/medical/dicom/current/output/chtml/part08/sect_9.3.5.html) specifies PDU type `04H`, a four-byte payload length, and one or more PDV items. Each item has a four-byte item length counting its following context ID and PDV bytes. This component requires exact complete extents, an item length covering the context and one mandatory message control byte, no trailing bytes, and at least one item. Impossible framing, overrun, underflow, and a wrong PDU type are source refusals before report addressing.

The report retains every PDV item start/end, fragment start/end, declared item length, context ID, control octet, and fragment byte count. [PS3.8 Annex E.2](https://dicom.nema.org/medical/dicom/current/output/chtml/part08/sect_e.2.html) gives bit 0 as command versus data set and bit 1 as last-fragment declaration. Bits 2 through 7 and the PDU reserved byte are sender-zero fields but not tested by a receiver; nonzero values remain observations, not predicted receiver rejection. Section 9.3.5 requires odd nonzero presentation context IDs. [Annex E.1](https://dicom.nema.org/medical/dicom/current/output/chtml/part08/chapter_E.html) supplies the sender expectations of a nonempty even-byte fragment and one message/context per P-DATA request. A parseable even or zero context ID, empty or odd-byte fragment, or mixed context IDs in this PDU remains a labeled sender-side deviation. This component does not infer association state, cross-PDU fragment order, negotiated presentation context or transfer syntax, command/data completeness, abstract syntax, receiver tolerance, or clinical meaning.

The variable fragment bytes are never parsed, decompressed or copied into individual observation rows. The full original base64 is retained solely to support exact replay. A cohashed alteration of an offset, length, sender observation, status, identity, effect or scope is refused as a replay of that source. A coherent different source may form a different valid report, but separate-original verification refuses substitution for the caller's supplied source. Neither historical replay nor exact bytes prove that a PDU was transmitted or accepted.

## Bounded intake and addressing

The PDU ceiling is 256 KiB, with at most 128 PDV items. Canonical source and report ceilings are 512 KiB and 1 MiB; native model/report nodes are limited to 2,048/8,192 with depth 12. Each public operation has one 32 MiB cumulative local software-work budget. Exact native types are required before cloning, parsing or hashing; bool is not int and subclasses are not silently normalized. The byte entry checks raw JSON byte size, depth, nodes, strings, signed64 integer grammar, duplicate members, floats and invalid escapes before the JSON decoder. Canonical base64 and exact PDU extents are required. The complete source/report capture, replay, comparison, encoding and hash-dependent fixed output are budgeted before the first local SHA-256. Separate-original verification funds both plans before either is hashed. These ceilings govern this software subset, not DICOM association negotiation or a clinical deployment.
